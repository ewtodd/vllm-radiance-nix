# Native W4A16 / W8A16 weight-only GEMM on gfx1201

Two opt-in, native weight-only paths for vLLM 0.29 on the R9700 (gfx1201). Both keep the
model's bf16 activations unquantized and dequantize the weight tile to bf16 inside the kernel,
so the only accuracy cost left is the stored weight precision. Default behaviour is unchanged.

| flag | checkpoint | kernel |
|---|---|---|
| `RADIANCE_MXFP4_W4A16=1` | Quark MXFP4, `input_tensors` absent (weight-only) | `radiance_w16_gemm` WT=0 |
| `RADIANCE_FP8_W8A16=1` | `quant_method: fp8`, `weight_block_size [128,128]` | `radiance_w16_gemm` WT=1 |

Both are off by default. With neither set, kernel selection, loading and throughput are
byte-for-byte the stock/radiance-v0.13 paths.

## What it does

* **One WMMA body, two weight formats.** `radiance_w16_gemm` in `radiance_mxfp4_fp8.hip` stages
  the weight tile through LDS and dequantizes it there: MXFP4 nibbles through a 16-entry E2M1
  bf16 table times the E8M0 block scale, e4m3 bytes widened through `v_cvt_pk_f32_fp8` times the
  128x128 block scale. The dequantized bf16 values are exactly what a bf16 reference model holds,
  so only the fp32 accumulation order differs from the reference. The multiply is the gfx1201
  **bf16** WMMA (`wmma_f32_16x16x16_bf16_w32_gfx12`); the activation is never converted.
* **Two tile geometries, chosen by M in the launcher.**
  * decode, `M<=16`: 16x128 tile (one 16-row M-fragment, eight N-waves of 16 columns), with
    **split-K** when the shape is narrow. Partials go to a torch-owned fp32 buffer and a small
    reduce kernel writes bf16. `w16_ksplit()` picks 1/2/4 splits from the N-block count so down
    and out projections (40 N-blocks) stop leaving the part half empty.
  * prefill, `M>16`: 128x64 tile (4x2 waves, 2x2 fragments per wave).
* **Scratch is allocated at weight-load time** (`process_weights_after_loading`), never inside
  CUDA-graph capture: 4 splits x 16 rows x max N fp32, 8 MiB at N<=32768.
* **Fail loudly.** The launcher throws on unsupported K/N; the Python classes raise at load on a
  shape the kernel cannot serve. There is no torch-dequant fallback in any forward path.

## Integration

* MXFP4: `radiance_mxfp4.kernel_class()` now returns the W4A16 class when only
  `RADIANCE_MXFP4_W4A16` is set, the existing W4A8 class when only `RADIANCE_MXFP4_W4A8` is set,
  and a small per-layer dispatcher when both are set. `patch_quark_mxfp4.py` is unchanged -- the
  deployed patch inserts exactly the class `kernel_class()` returns. The W4A16 class accepts
  `activation_quant_key is None` (the Quark weight-only config) and declares its own
  `process_weights_after_loading` / `apply_weights`; it does not touch `QuarkOCP_MX`'s loader.
* FP8: `radiance_kernels.install_w8a16_hook()` (called from `install_all()` when
  `RADIANCE_FP8_W8A16=1`) puts `radiance_fp8.RadianceFp8W8A16Kernel` at the head of
  `_POSSIBLE_FP8_BLOCK_KERNELS[ROCM]` and `_POSSIBLE_WFP8A16_KERNELS[ROCM]` at plugin time. The
  kernel subclasses `Fp8BlockScaledMMLinearKernel` with `apply_input_quant = False`, consumes
  `weight_scale_inv` as fp32, and is also loadable by `CompressedTensorsW8A16Fp8`. The
  `RADIANCE_PRESHUFFLE` hook skips layers tagged `_radiance_w8a16`.
* Weight layouts: MXFP4 checkpoint order `[N, K/2]` + `[K/32, N]` e8m0, or the bf16 fragment
  order from `permute_w16()` when `RADIANCE_MXFP4_WPERM=1` (the flag now drives both the loader
  and the kernel, as for W4A8). FP8 is `[N, K]` e4m3 + `[N/128, K/128]` fp32.

## Files

* `radiance_mxfp4_fp8.hip` -- kernels + launchers (`launch_w4a16`, `launch_w8a16`,
  `radiance_w16_reduce`); the existing Nix/Docker hipcc rule compiles them with no extra rule.
* `radiance_mxfp4.py` -- `permute_w16`, `RadianceMxfp4W4A16LinearKernel`, dispatcher,
  `radiance::mxfp4_linear_w4a16` op.
* `radiance_fp8.py` -- W8A16 kernel class and `radiance::fp8_w8a16_mm` op.
* `radiance_kernels.py` -- `install_w8a16_hook`, preshuffle skip.
* `w16-tests/` -- unit test, kernel benchmark, logits capture/compare, serve/bench wrappers.

## Serving

```bash
# W4A16 (Quark RTN checkpoint, weight-only config dir)
PYTHONPATH=/path/to/shadow RADIANCE_MXFP4_W4A16=1 \
vllm serve /scratch/vllm-models/Swift-1.5-Qwen3.8-27b-Quark-RTN-MXFP4-W4A16 \
  --tensor-parallel-size 2 --max-model-len 8192 --attention-backend R4D

# W8A16 (e4m3 block-scaled checkpoint)
PYTHONPATH=/path/to/shadow RADIANCE_FP8_W8A16=1 \
vllm serve /scratch/vllm-models/Swift-1.5-Qwen3.8-27b-FP8 \
  --tensor-parallel-size 2 --max-model-len 8192 --attention-backend R4D
```

`RADIANCE_MXFP4_WPERM=1` may accompany W4A16; it is not required.

## Verification (2x R9700, TP=2, 27B Swift-1.5; no DFlash2 drafter model, but `env.sh` leaves the radiance dynamic/fast draft head on)

* Kernel: `w16-tests/test_kernels.py` sweeps all six per-rank model shapes at M in
  {1,4,32,256,2048}, both W4A16 layouts: 90 cases, 0 failures, max rel error 2.9e-3 against an
  f32 dequant (bar 1e-2).
* Logits ("The capital of France is", W4A16 layout=WPERM=1): W4A16 vs the bf16-dequantized
  reference rel=0.0069, corr=1.0000, top-1 exact, top-5 5/5; vs the bf16 base rel=0.1594 (the
  card's weight-quantization number is 0.159). W8A16 vs its dequantized reference rel=0.0103,
  corr=0.9999, top-1 exact, top-5 5/5; vs the bf16 base rel=0.0233 (card: 0.024).
* Speed, same harness/config per pair (decode = 128 greedy tokens, batch 1; prefill = one
  8192-token prompt). `env.sh` sets `RADIANCE_DYNAMIC_DRAFT=1` and `RADIANCE_FAST_DRAFT=1`, so
  these decode numbers include the radiance draft head, not a bare target forward pass:

| arm | decode ms/step | prefill 8k tok/s |
|---|---:|---:|
| W4A16 (compiled V2, WPERM=1) | 23.61 | 1499 |
| W4A8 (compiled V2) | 18.04 | 2364 |
| **ratio** | **0.76x** | 0.63x |
| W8A16 (eager V1) | 46.48 | 1389 |
| W8A8 (eager V1) | 65.17 | 1674 |
| **ratio** | **1.40x** | 0.83x |
| W8A16 (compiled V2, reference only) | 37.52 | 1515 |

The W8 ratio pair is eager because the stock W8A8 path cannot capture cudagraphs with
`RADIANCE_PRESHUFFLE=1` on this stack (pre-existing; unrelated to these kernels); the W8A16 kernel
itself captures fine (37.52 ms/step). The W4 pair is compiled as in production.

### End-to-end accuracy (check-source, seed 1234, fp16 KV, targets only)

| arm (weights / activations / KV) | gsm8k 300 thinking | gsm8k 300 nothink | gsm8k-chat 200 medium |
|---|---:|---:|---:|
| W4A16 / bf16 / fp16 | **0.9733 / 0.9733** | **0.9133 / 0.9133** | **0.9850 / 0.9850** |
| W4A8 same checkpoint, same 300 | 0.9667 / 0.9667 | full set: 0.9242 / 0.9265 | 0.980 / 0.980 |
| W8A16 / bf16 / fp16 | **0.8667 / 0.8600** | 0.8567 / 0.8667 | 0.9800 / 0.9800 |
| W8A8 same checkpoint, same 300 | 0.8100 / 0.8133 | 0.8500 / 0.8833 | 0.980 / 0.980 |
| bf16 base | full set pending | full set pending | 0.985 / 0.985 |

Labels per run: weights / activations / KV-cache, e.g. `MXFP4 RTN (W4A16) / bf16 / fp16`.
W4A16 sits at the dequantized end of the range (within one item of the bf16 base on chat, above
W4A8 on the same 300 thinking/chat subset). W8A16 recovers **+5.7 strict / +4.7 flexible** over
W8A8 on the same 300-item thinking subset, and is within noise on nothink/chat, where the
dynamic-activation loss is smaller. Both new paths are between the A8 path and the base, as
expected.

### KV-cache context (W8A16, fp16 KV, 2x R9700)

KV pool after load: target FP8 checkpoint served with `RADIANCE_FP8_W8A16=1`, `--kv-cache-dtype
auto` (fp16), TP2, `--max-model-len 262144`, `--max-num-seqs 4`, PIECEWISE graphs, V2 runner.
"concurrency" is vLLM's `Maximum concurrency for 262,144 tokens per request`.

| config | gpu-mem-util | KV pool | concurrency @ 262,144 |
|---|---:|---:|---:|
| target only | 0.95 | 412,819 tokens | 1.57x |
| + DFlash2 drafter (7 tokens, TP2, 262,144) | 0.95 | 269,310 tokens | 1.03x |
| + DFlash2 drafter | 0.98 | 317,213 tokens | 1.21x |

The DFlash2 drafter costs a flat ~143.5k tokens of KV headroom (it is a second, 2 GB TP2 model
with its own 262k KV). At 0.98 the full native 262,144 context fits with ~21% headroom -- one
full-context stream plus a little, not several concurrent 256k streams. fp8 KV roughly doubles the
pool at the accuracy cost documented on the cards.

### No regressions

* W4A8: the `Swift-1.5-Quark-RTN-MXFP4` checkpoint served through the new `.so` and the modified
  `radiance_mxfp4.py` (only `RADIANCE_MXFP4`/`RADIANCE_MXFP4_W4A8` set) produced logits
  **bit-identical** to the stock deployed build (maxabs 0.0, `torch.equal` true).
* ParoQuant: the in-serve CHECKALL on `Qwen3.8-27B-PARO-int5` reports rel 0.00000 on the decode
  shapes and 4e-5/7e-5 on the M=5 calls, unchanged from the documented gates.
* W8A8: with `RADIANCE_FP8_W8A16` unset the hook returns before touching the kernel list; the FP8
  checkpoint loads and generates on the stock W8A8 path. (The pre-existing
  `RADIANCE_PRESHUFFLE + cudagraph` capture failure on this stack reproduces with and without
  these changes; the campaign baseline runs eager.)

## Reproduction

```bash
cd /scratch/w16
source env.sh
export PYTHONPATH=/scratch/w16/shadow:/scratch/w16      # or the Nix-built site-packages
export VLLM_USE_V2_MODEL_RUNNER=0 BENCH_EAGER=1
# W4A16
bash run_eval_arm.sh /scratch/vllm-models/Swift-1.5-Qwen3.8-27b-Quark-RTN-MXFP4-W4A16 \
  8301 w4a16 "MXFP4 RTN (W4A16, dequant-to-bf16)" bf16 \
  RADIANCE_MXFP4_W4A16=1 RADIANCE_MXFP4_WPERM=1
# W8A16
bash run_eval_arm.sh /scratch/vllm-models/Swift-1.5-Qwen3.8-27b-FP8 \
  8302 w8a16 "FP8 e4m3 (W8A16, dequant-to-bf16)" bf16 RADIANCE_FP8_W8A16=1
# kernel unit test (all model shapes, M 1..2048, both layouts)
HIP_VISIBLE_DEVICES=0 python test_kernels.py shadow/radiance_mxfp4_fp8.so
# logits: capture through the model + compare to the saved dequantized reference
RADIANCE_MXFP4_W4A16=1 RADIANCE_MXFP4_WPERM=1 \
  bash run_serve_logits.sh <model> /scratch/w16/logits_w4a16_final.pt
python compare_logits.py --a logits_w4a16_final.pt \
  --b /scratch/models/swift15/logits_rtn.pt
```

## What is left

* Full-set (1319) GSM8K for the two new paths and the bf16-base raw rows; the A8 rows in
  `W4A16_W8A16.md` are the existing campaign full sets.
* W4A16 prefill is 0.63x of W4A8 (not gated by the 0.7x floor, which is decode). A dedicated
  bf16-WMMA prefill tile or a fused conversion would close it.
* The W8A16 kernel is itself graph-capturable: with `enforce_eager=False` it captured full CUDA
  graphs and ran 37.5 ms/step (`w16-tests/results/w8a16.json`). The eager number in the table is
  used only so the W8A16-vs-W8A8 pair is like-for-like -- the *stock W8A8* path cannot run
  compiled on this stack with `RADIANCE_PRESHUFFLE=1` (engine init fails with a preshuffle
  layout/stride mismatch), so eager is the only available W8A8 baseline.
* `CompressedTensorsW8A16Fp8` is wired (the kernel is loadable from both registries) but was only
  exercised through the `quant_method: fp8` Fp8Config path.
* The W4A16 path is selected by `RADIANCE_MXFP4_W4A16=1` and the checkpoint's weight-only config;
  a W4A4-declared checkpoint (`input_tensors` present) is intentionally left on the A8 path.
